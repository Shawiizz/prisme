Prisme is a Rust engine that plays the audio, an application around it that holds the library, the settings and the controllers, and an interface that shows it all. The engine never waits for anything else: everything else talks to it without ever holding it up.

## The layout of the repository

```text
apps/
  prisme-desktop/    the application (Tauri v2); its interface is in frontend/ (Angular)
  prisme-setup/      the Windows installer's window
  prisme-cli/        the whole chain from the command line, without the interface
crates/
  prisme-timecode/   timecode vinyl decoder: speed, direction, absolute position
  prisme-engine/     real-time engine: decks, vinyl control, mixer, sampler
  prisme-dsp/        real-time processing: filters, EQ, effects, limiter
  prisme-audio-io/   sound cards behind a small interface
  prisme-media/      audio file decoding, tags and cover art
  prisme-analysis/   waveforms, tempo and beat grid, musical key
  prisme-library/    track database, folder scanning, background analysis
  prisme-stems/      source separation on the GPU or the processor
  prisme-import/     Serato and rekordbox import, rekordbox and playlist export
  prisme-control/    MIDI and HID controller messages, mappings and profiles, the list of actions
  prisme-actions/    what each action decides: its rules, its light, what the screen shows
  prisme-session/    settings files with atomic writes
frontend/            the interface (Angular)
design/              the design system: DESIGN.md and the reference screens
tools/controllers/   the converter of Mixxx mappings into profiles
website/             this site (Astro and Starlight)
```

## The crates

| Crate | What it does |
| --- | --- |
| `prisme-timecode` | Turns the signal of a turntable playing a timecode record into a speed, a direction and a position on the record. The records it reads are a list of formats, by maker, record and side, which the settings offer as listed: Serato's CV02 (sides A and B) and Control CD today, another record being another entry. A decoder written from scratch, with a simulated turntable for tests and for trying vinyl control without one. |
| `prisme-engine` | The audio engine. Each deck plays a track through a playhead that moves at any speed in either direction, driven by its own play and tempo or by a timecode record (absolute or relative). Sync to a leader deck, key lock, a chain of beat effects, a sampler and passthrough per deck; the software mixer (trim, EQ with kills, filter, faders, crossfader, microphone, aux, master limiter and balance, booth); the headphones preview; recording. |
| `prisme-dsp` | The processing the engine uses, all of it real-time safe: the state-variable filter the rest is built from, the 3-band EQ, the one-knob filter, the beat effects, the limiter, parameter smoothing. |
| `prisme-audio-io` | The sound card. The rest of Prisme sees one callback per audio period, with the interleaved input (the turntables) and output. Behind it: WASAPI and ASIO on Windows, CoreAudio on macOS and iOS, ALSA and JACK on Linux, AAudio on Android, and a USB driver of Prisme's own for the sound cards a phone's system reaches only in part. |
| `prisme-media` | Decodes a whole track into memory, as stereo 32-bit floats: scratches and needle drops need any point of the track at once. Decoding happens on a worker thread, and a track plays while it is still being decoded. Also the tags and the cover art. |
| `prisme-analysis` | Waveforms (the peak level and the energy of the low, mid and high bands of each slice, computed as the track is decoded), tempo and beat grid, musical key with its Camelot code, loudness, and where each stem plays. |
| `prisme-library` | The SQLite database of the tracks, their analysis (redone when the file or the algorithms change), cues, crates and set history; scanning the music folders; smart crates; duplicates; the background analysis, at low priority. |
| `prisme-stems` | Stem separation with RoFormer networks (Mel-Band and BS-RoFormer), on the GPU through wgpu (DirectX 12 or Vulkan, Metal), or on the processor. |
| `prisme-import` | Crates, cues, loops, beat grids, colours and ratings from Serato and rekordbox, merged without overwriting what Prisme already has; the export to rekordbox and to playlists. |
| `prisme-control` | MIDI and HID controllers: what their messages and reports say, which action each control drives, the messages that light them, and the [profiles](/docs/controllers/profiles/) of the models Prisme knows. It also lists every action of the app, with its id, group, name and kind (`target.rs`, `listed.rs`): the keyboard, the command palette and the controllers all name the same actions. The actions are only names here. |
| `prisme-actions` | What each action decides, apart from what it drives: the rules of its keys (a CDJ's cue, a SYNC tapped or held, a key held that repeats), the pads and their pages, the lengths of loops and rolls, the order actions keep among themselves. And what the app looks like at a moment, read once (a *view*): what each light and fader of a controller shows, and what the screen shows of each deck. The application performs the actions by these rules, whoever asks. |
| `prisme-session` | Settings kept in JSON files, written atomically (a temporary file, then a rename), so that a crash never leaves half a file. |

## The real-time rules

The audio thread runs the engine inside the sound card's callback, a few milliseconds at a time. Anything that may wait there, even rarely, is an audible click. So the audio thread **never allocates, locks or frees memory**:

- The application sends the engine **commands** through a lock-free queue (`rtrb`): load this track, play, move the tempo, set this effect.
- The engine **publishes its state** (positions, speeds, levels, vinyl signal…) in a triple buffer, about a hundred times a second; the application reads the latest whenever it wants, without ever blocking the engine.
- What the engine **replaces** (a track, a timecode decoder) goes back to the control side through another queue, to be freed there. If that queue is ever full, the object is leaked rather than freed on the audio thread.
- What the engine needs is built beforehand on the control side, its buffers at the largest size a period can have.
- The processing of `prisme-dsp` changes its parameters without clicks and keeps the arithmetic fast near silence.

<Aside type="caution">
A change to `prisme-engine`, `prisme-dsp` or `prisme-timecode` must keep these rules: on the audio path, no `Vec` that grows, no `Box` made or dropped, no `Mutex`.
</Aside>

## The application

`apps/prisme-desktop` is the Tauri application, the same on a computer and on a phone. It owns the running audio, the library and everything kept from one start to the next:

- **The audio**: the sound card stream lives on a thread of its own, with the engine in its callback. A watchdog restarts it when its device comes back after a loss, when the engine failed or when the driver stopped calling, with the decks where they were.
- **Commands**: what the interface can ask, by domain (`src/commands`): decks, mixer, effects, library, crates, stems, controllers…
- **Actions**: every action, whoever asks for it (a controller, a key, a click on the screen, the command palette), goes in by one door (`src/actions`) and is performed in Rust. Each keeps its order among the actions of its lane (a deck's track, a deck's settings, the mixer, the library…): it is done at once on the thread asking for it, unless its lane has one waiting. One that opens or writes a file is left to the lane's worker: the actions of the other lanes never wait for it.
- **The clock**: about 60 times a second, the backend reads the engine's state once into a view, and from it fires the keys held, lights the controllers, moves the previews and ranks the library's rows.
- **The status stream**: the clock then tells the interface what changed, on a channel of its own. The state is cut into sections (decks, tracks, mixer, pads, library, settings, controllers, audio…), each with a revision: only the sections that moved are sent, and nothing at all while nothing moves. A turntable's signal goes on a channel of its own while its oscilloscope is shown; the rest goes as events.
- **The library view**: the list browsed, its search, its sort and its selection live in Rust, every track in memory; the interface draws only the rows it shows.
- **Controllers**: a mapped control's messages drive the actions from the MIDI or HID thread, with the time each message arrived, so a scratch follows your hand. The interface is only told of the few actions it does itself: its windows, the focus of its search.
- **Background work**: loading a track in two steps (playable at once, the rest on a worker thread), the analysis of the library, the stem separation queue, writing tags, recording to a file.
- **Kept on disk**, in the data folder: `preferences.json`, `controllers.json`, `session.json` (what the decks held, to put them back after a crash), `library.sqlite`, the logs (one file a day, a week kept), your own controller profiles.

## The interface

`frontend` is an Angular application. Its parts:

- The interface shows what the backend computes and sends it gestures: a key pressed or let go, a fader moved, a click. It decides nothing of what an action does. The [keyboard](/docs/interface/keyboard/), the command palette and the [controllers](/docs/controllers/actions/) all drive the same actions, which the backend lists (`list_targets`) and names.
- `core/models/status.ts` holds the types of the status stream, written from the backend's own by a test (`PRISME_WRITE_TYPES=1 cargo test -p prisme-desktop status_stream`), never by hand.
- `core/services` talks to the application: the status stream, the library, the mixer, the effects, the sampler…
- `features` holds the screens: decks, mixer, library, turntables, settings, the palette, the phone layout.
- `core/i18n`: the interface is written in English, which is also the key of each text; `fr.json` holds the French. `actions.json`, the names of the actions to translate, is written by the tests of `prisme-control`.
- The look comes from the design system in `design/DESIGN.md`: the tokens and ready-made classes in `frontend/src/styles`.

## The command line

`apps/prisme-cli` runs the same engine, sound card and decoder without the interface: to play a track, try vinyl control with a simulated or a real turntable, measure the latency or analyse files. See [Command line](/docs/develop/cli/).
